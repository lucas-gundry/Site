The missing-logs investigation where I was wrong

Okta · Elastic Agent · Elasticsearch · Python

Problem

After a reboot, the agent that ships Okta's audit log into my SIEM logged Exporting failed. Dropping data. It had tried to send events while Elasticsearch was still starting up.

For a SIEM, losing security logs without any warning is about the worst failure there is. Every detection downstream would be blind, and nothing would tell you. So I took it seriously, and I wrote up a root cause: during an outage, delivery is at-most-once, so events can be silently lost. I drafted six fix options.

That root cause was wrong.

What I built

Before applying any fix, I built a way to measure loss directly: a gap check.

  • For a time window, it lists every event ID in Okta's audit log and looks each one up in Elastic.
  • Each missing event is labeled LOST (before the collector's bookmark, so it will never be fetched again) or PENDING (the next poll should pick it up).
  • It is read-only on both sides: a log-read-only Okta app and a read-only Elastic account. Its exit codes are simple: 0 means nothing missing, 1 means events missing, 2 means the check couldn't run.
  • It has unit tests that use fakes only. Its first live run failed on a format my test fixtures had guessed wrong. I fixed it, and the fixtures now copy the real format.

How I tested it

TestOktaElasticLost
History check across all 5 boots since setup1091090
A 19-minute outage while the agent kept running23230
A planned outage with an agent restart in the middle220

Every match was by event ID, not by count.

The decisive case was one boot where the "dropped" batch held 3 events instead of 1. The two new events were stored 12 seconds after the "Dropping data" line, 3 seconds after Elasticsearch came up, and before the next poll. My theory said a re-fetch could bring back only the newest event. Both came back, before any re-fetch could happen. So the batch was retried and delivered.

In the restart test, an event was still waiting in memory when I restarted the agent. Its saved bookmark hadn't moved, so it fetched the event again and stored it. Only then did the bookmark move forward.

The retraction

I closed the item as not a bug, with no fix applied. I didn't delete the wrong analysis. It stays in the decision record, struck through, next to a note on where the reasoning went wrong:

  • I read a scary log line as proof of loss. It actually counted a failed send attempt, not a discarded event.
  • My theory rested on a 1-event batch. With one event, a retry and a re-fetch look exactly the same.
  • Nobody had seen the bookmark move before delivery. I'd only read it after recovery.

What still isn't tested, said out loud: an outage longer than the agent's in-memory queue, and a multi-event batch across an agent restart. The control for those is the gap check itself, now running every hour and alerting on any LOST event and on "couldn't run". That's the next write-up.

The investigation also turned up a real operational issue. If the agent restarts while Elasticsearch is down, it can't start until Elasticsearch is back. Collection pauses, but nothing is lost, because it resumes from its bookmark.

What I learned

  • A log message is a hypothesis, not a finding.
  • Build the measurement before the fix. The gap check took less time than any of the six fixes, and it made all of them unnecessary.
  • Small samples can't separate explanations. I needed the one case where two theories predict different things.
  • Keep the wrong reasoning in the record. A retraction you can read is worth more than a clean history. It shows the next person which trap to avoid.
  • Matching by ID beats matching by count. Equal totals can hide a lost event that's offset by a duplicate.
