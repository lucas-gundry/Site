Least privilege and alerts that tell me when they're broken

Elasticsearch roles · systemd · healthchecks.io · Python

Problem

My SIEM takes a snapshot every night, and Okta events stream in all day. Either one could fail quietly. Nothing told me if a nightly backup failed or if security events went missing.

Any fix has two traps. The account that monitors backups shouldn't be able to delete or restore them. And an alert that runs on a schedule fails the worst way of all: it stops running and says nothing.

What I built

Separate accounts, each with one job

  • A read-only analyst account for searches and status checks. It has no writes, no deletes, and no security settings.
  • A named admin account for changes. I run anything that needs it myself.
  • The built-in superuser is for setup and break-glass only.
  • If a read-only check is refused, it reports the refusal. It never switches to a stronger account to get around it.

To monitor backups, the analyst role got exactly two read-only privileges: view snapshot status and view the snapshot policy. That's all it got.

Two scheduled checks, with three ways to alert

  • A gap check every hour: every Okta event ID must be in Elastic (see the investigation).
  • A snapshot check daily, an hour after the nightly backup, scheduled in UTC so daylight saving can't shift it. Six rules, all decided in code:
    1. The snapshot scheduler is running.
    2. The policy exists and has the schedule the check expects. If the policy changes, the check fails safe.
    3. A successful snapshot exists since the last one was due.
    4. The newest snapshot fully succeeded, every shard.
    5. No failure has been recorded since the last success.
    6. The oldest snapshot is not past retention. If old snapshots aren't being deleted, the disk will fill silently.
  • Each check reports to healthchecks.io, a dead man's switch. It emails me on a failure, or when no report arrives on time.
  • Only one line leaves the machine: a status word, rule numbers, and counts. No hostnames, snapshot names, or event data. The wrapper refuses to send anything else.
  • Each job loads only its own ping URL, from its own file, readable only by its owner.

A subtle one, rule 3: "the newest snapshot is under 26 hours old" sounds right, but it's wrong. When the check runs an hour after the backup, a missed night leaves yesterday's snapshot only 25 hours old, so that rule would pass. The check asks a different question: is there a success since the last time one was due?

How I tested it

The role, tested by what it refuses

  • A check script tests the allowed reads and the refused actions: create, delete, and restore a snapshot; change, delete, or run the policy. Running the policy now is another way to create a snapshot, so it has to be refused too.
  • The refused actions target a repository and policy that don't exist. A "not found" answer would mean the action was allowed to get that far, so it fails the check. Only a "forbidden" passes.
  • Before the change: 17 of 19. The two new reads were refused, which proves the checks catch missing access. After: 19 of 19. Every write and restore was still refused.

The four alert states, tested live

For each test I watched the machine's own log and checked what reached my inbox.

One more case: I ran the real snapshot check with a made-up password. It got a 401, exited with an error, and sent nothing. An authentication error with no summary shouldn't turn into a report.

What went wrong on the way

The first two clean runs failed with "missing settings file". I had created it on the wrong machine. The wrapper refused to run and sent nothing, as designed. The setup command has a hostname check for exactly this mistake.

What I learned

  • Prove least privilege by what's refused. A role that passes every read test might still be able to delete your backups.
  • Make "allowed" impossible to mistake for "refused". Testing against things that don't exist turns a silent pass into a visible failure.
  • Silence is a failure mode. A check that only alerts when it runs can't tell you it stopped. An outside dead man's switch can.
  • Choose what leaves the network. The alert body is a short, fixed format, so monitoring doesn't leak internal names.
  • Know the limits. The tests prove the alert path, not a real backup failure. Making one would need admin changes. A machine that is off and one that skipped a run look the same: both are silence.
