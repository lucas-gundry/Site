Making a cloud SIEM quieter, and finding what it couldn't see

Datadog Cloud SIEM · AWS CloudTrail · Okta · SentinelOne

Professional work at a fintech company (contract). The employer and internal details are left out.

The SIEM raised about 1,100 signals a month, most of them harmless. I removed about 480 a month with narrow suppressions that expire, found log sources that weren't arriving, gave identity one shared key across systems, and used it to ship the first detection that follows an account takeover across more than one system.

The problem

Most signals came from known, harmless activity in the normal course of work, so the real ones were easy to miss. Volume was only half of it: a quiet SIEM can also mean logs that never arrive.

Cutting noise without hiding things

I started with the highest-volume rules. For each known-benign pattern I wrote a suppression scoped to one user or service, not the whole rule, so the rule still fires for everyone else. Every suppression has an expiry date, so it comes back for review instead of living forever.

Some rules alerted on attempts rather than outcomes. A rule that fired on every Log4Shell exploit attempt, for example, was one of the largest sources on its own. I retired attempt-only rules like that in favor of rules that fire when an attempt succeeds. I also moved SentinelOne exclusions off device groups that turned out to be empty, and found one suppression that had never matched anything.

Checking what the SIEM could see

I compared the sources the SIEM should have with what it was actually receiving. CloudTrail wasn't arriving from most AWS accounts, and some integrations were set up but had stopped sending.

One identity key across systems

CloudTrail, Okta and SentinelOne each name a person differently. I normalized all three to the user's email address, so one search follows a person across cloud, identity and endpoint activity.

A cross-system account-takeover detection

With the shared key in place, I built the first detection that correlates across systems: a sign-in from a new country, followed within a day by a sensitive change in the password manager, Google Workspace, the web application firewall or AWS. Before shipping it, I checked that every input carried the email field, because a correlation on a missing key fails silently.

It shipped at informational severity and is reviewed during a learning period before it can be promoted to an alert, so it proves its accuracy before it can page anyone.

Two automations

  • Every 15 minutes, signals that SentinelOne or the managed detection and response provider have already resolved as false positive or benign are archived, with their notes. Analysts start with the ones that still need a person.
  • A scheduled audit checks the web application firewall's configuration against what it should be.

How I checked

Each suppression covers one user or service, so the rule keeps firing for everyone else. Each one expires, so it gets reviewed again instead of quietly hiding activity forever.

Limits

Fewer signals is a volume measure, not proof of better detection. The correlation is new, and its review period is what will show how accurate it is.

Related lab work
