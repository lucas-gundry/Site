Cutting SIEM noise without losing coverage

Elastic · Sumo Logic · AWS · detection tuning

What this demonstrates: running detection tuning as an operational practice: finding where the noise comes from, tuning it against how people actually work, and checking that quieter detections can still fire.

Professional work at a previous employer. The employer and internal details are left out.

Problem

I led detection and response for the SOC. The team got a lot of alerts, and many of them weren't attacks. File integrity monitoring fired on routine changes, and other detections flagged the normal course of people's work. When many alerts are false positives, the real ones are easier to miss.

What I did

Found the noise

I used dashboards to rank detections by alert volume, then started with the highest.

Tuned against normal work

Two kinds of change did most of the work:

  • Correlating alerts with normal work. Before tuning an alert, I looked at what was actually behind it. For AWS Systems Manager (SSM) logins, I reviewed which users started the sessions and the commands they ran, and confirmed it was normal work before tuning the detection around it.
  • Reducing built-in rules that over-alerted. Some of the SIEMs' built-in rules over-alerted, so I reduced them.

Checked that quiet detections still worked

Less noise is only good if real detections still fire. For detections that hadn't fired in a long time, I looked for a way to test them, triggering the activity on purpose where I could. That wasn't always possible.

Result

I tracked alert volume on dashboards month over month, by alert type and count. Alert volume dropped by about 30%, while keeping useful coverage and giving responders more context.

Limits

  • The 30% is alert volume, measured on dashboards. It isn't a measure of detection quality on its own.
  • Triggering a quiet detection on purpose wasn't always possible, so not all of them could be tested that way.

Related lab work

My lab write-ups show the same habits in public detail: a detection tested for when it should fire and when it shouldn't, and checking test data against real events before turning a rule on.
