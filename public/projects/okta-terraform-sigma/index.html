Identity as code, and a detection I tested both ways

Okta · Terraform · Elastic · Sigma

Problem

Identity is the front door of most companies. When people change the directory by hand, nobody reviews those changes and nothing records why they were made. A detection rule that has only ever been read, and never run against real events, might never fire, or might fire all day.

I wanted both halves done properly. The directory should be reviewable and repeatable. The first detection should be proven to fire on an attack and stay quiet on normal mistakes.

What I built

The directory, as code

  • A fake company of 30 employees in 8 departments and 13 groups, built in Okta with Terraform.
  • A CSV file acts as the HR system of record. Joiners and leavers are edits to the CSV, then terraform plan, a review, and an apply. A change made by hand in Okta shows up as drift on the next plan.
  • Every plan is saved and reviewed before it's applied. Nothing gets applied without that review.
  • The admin API token works only from my home network, so a stolen copy is useless anywhere else. Admin MFA uses push with number matching, which defeats MFA-fatigue attacks.

The log pipeline

  • Okta's audit log streams into Elastic through Elastic Agent.
  • The collector signs in as its own OAuth service app with one read-only scope. It does not reuse Terraform's token, which can create and change users.

The detection

  • A Sigma rule that matches one failed Okta sign-in, converted to an Elastic query with a field-mapping pipeline.
  • An Elastic threshold rule on top of it: 5 or more failures for one user in a 5-minute run suggests password guessing (MITRE ATT&CK T1110.001).
  • The rule is deployed by a script that uses a narrowly scoped API key with a 90-day expiry.

Why the threshold lives in Elastic, not Sigma: I tested the converters. The Lucene backend doesn't convert Sigma correlation rules. The ES|QL backend makes a different kind of rule with fixed time buckets. So the Sigma file holds the base rule, and the Elastic rule holds the count. The query the converter produces matches the deployed rule exactly.

How I tested it

Test cases kept next to the rule

CaseExpectedWhy
5 failures for one user in 4 minutesFiresTrue positive: guessing against one account
4 failures, then a successQuietFalse positive avoided: someone who forgot their password
5 failures spread over 5 usersQuietThis rule is per-user. Password spraying needs its own rule

Live test against real Okta events

  • One test user had 6 failed sign-ins in a burst. One alert, count 6.
  • A second user had 4 failures, below the threshold. No alert.
  • The first user had a second burst of 7 a few minutes later. A second alert, count 7. The bursts were counted separately (6 and 7, not 13).

Revoking the collector's access

  • I deactivated the collector's Okta app on purpose. It was refused 2 seconds later.
  • Turning the app back on didn't restore access: it had lost its admin role and its scope grant. The console still showed the scope as granted. Okta's log proved it wasn't.
  • Nothing was lost. The collector picked up from its bookmark and caught up on 31 events, with no gaps and no duplicates. I wrote a recovery checklist from it.

What I learned

  • Test the quiet cases too. A rule that fires on everything passes the "does it fire" test. The forgot-my-password case is what shows the threshold is right.
  • Be honest about what a test covers. My test users were staged, not active, so these failures were "can't sign in" events, not real wrong passwords, and no lockout applied. Testing a real wrong password and a lockout is the next step.
  • When the UI and the logs disagree, trust the logs.
  • Correlate on the stable user ID, not the login name. Names change, and logs keep the name a person had at the time of the event.
  • Check your tools' limits early. The Sigma converter couldn't express the threshold. Finding that out on day one shaped where each piece lives.
