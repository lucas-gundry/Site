Missing logs that weren't missing

Okta · Elastic Agent · Elasticsearch · Python

What this demonstrates: Root-cause analysis on security telemetry. I measured instead of trusting an alarming log line, built an independent check that matches every event by ID, and dropped my own conclusion when the evidence contradicted it.

Homelab project: a fake company, real systems, my own test traffic.

Problem

After I rebooted the lab, the agent that ships Okta's audit log to my SIEM logged Exporting failed. Dropping data. It had tried to send events while Elasticsearch was still starting.

Losing security logs with no warning would be serious. Every detection after that point would be missing data, and nothing would tell me. I read the line as proof of loss and wrote up a root cause: during an outage, events can be lost for good. I drafted six possible fixes.

I was wrong, and I only found out by measuring.

What I built

Before changing anything, I wrote a gap check to measure loss directly. It takes a time window and lists every event ID in Okta's audit log. Then it looks up each ID in Elastic.

A missing event is LOST if it's older than the agent's bookmark, because the agent won't fetch it again. It's PENDING if it's newer, because the next poll should pick it up.

The check only reads. It uses an Okta app that can only read logs, and a read-only Elastic account. Exit code 0 means nothing is missing, 1 means events are missing, and 2 means the check couldn't run.

It started with 25 unit tests that use fakes. The first live run failed because my test data had guessed the agent's file format wrong. I fixed the code and copied the real format into the tests.

I matched every event by its ID.

One boot settled it. The dropped batch held 3 events: the bookmark event and two new ones. Both new events were stored 12 seconds after the "Dropping data" line and 3 seconds after Elasticsearch came up. That was before the next poll. If my theory were right, only the newest event could have come back, and only on that next poll. Both came back early, so the agent had retried the batch.

In the restart test, one event was still waiting in memory when I restarted the agent. Its bookmark hadn't moved, so it fetched the event again after the restart and stored it. The bookmark moved only after that.

The retraction

I closed the issue as not a bug and applied no fix. I kept my wrong analysis in the decision record, struck through, with a note on where it went wrong.

  • I treated a log message as proof. The line counts failed send attempts. It doesn't count lost events.
  • I based the theory on a batch of 1 event. With one event, a retry and a re-fetch look the same.
  • I never saw the bookmark move before delivery. I only looked at it after things had recovered.

Still untested: an outage longer than the agent's memory queue can hold, and a multi-event batch across an agent restart. The gap check covers those cases. It now runs every hour and alerts me on any LOST event or if it can't run. The next write-up covers that alerting.

The investigation did find one real issue. If the agent restarts while Elasticsearch is down, it can't start until Elasticsearch is back. Collection pauses, but nothing is lost, because it resumes from its bookmark.

What I learned

  • A log line is something to check. It isn't a finding.
  • The gap check took less time to build than any of the six fixes, and it showed I didn't need them.
  • My small samples couldn't tell the two explanations apart. I needed the one case where they predicted different results.
  • I keep wrong analysis in the record. Whoever reads it next, including me, can see what I got wrong and why.
