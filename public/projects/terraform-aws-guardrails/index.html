Terraform on AWS, with the guardrails tested

AWS · Terraform · IAM Identity Center · S3 · Checkov

Problem

Infrastructure code is only as safe as the way it runs. If Terraform runs with a long-lived access key, a leaked laptop is a leaked cloud account. If it applies changes nobody read, the review step is decoration. And its state file, the record of everything it built, can hold secrets.

Before building my lab's real AWS layer, I wanted the Terraform workflow itself to be something I'd defend in a review. I did it in four small steps, on cheap S3 buckets, and tested each guardrail instead of assuming it worked.

What I built

The AWS side is two accounts. The management account holds billing and identity, and only its root user can sign in to it, with MFA and no access keys. My everyday sign-in, through IAM Identity Center with MFA, can reach only a separate lab account. The command line gets temporary credentials for that one account. There's no access key to leak or rotate.

Terraform has a seatbelt too: it's told which account it may touch, and it refuses to run anywhere else. The account ID comes from a file that Git ignores. It isn't a secret, but it identifies a real account, so it stays out of the repo.

How I tested it

Step 1: plan to a file, apply that file

A first bucket, private and encrypted. New S3 buckets are already both by default, but I wrote it down anyway, so a reviewer or a scanner can see it, and a future default change at AWS can't quietly undo it. I saved the plan to a file and applied that exact file, then read the bucket's settings straight from AWS instead of trusting "Apply complete". The teardown got the same treatment: a saved destroy plan, applied, then a check that AWS answered 404.

Step 2: taking over a bucket built by hand

Real environments have things somebody clicked together. I made a bucket in the console and brought it under Terraform with import blocks, which go through plan and review like any other change. (The older import command writes state immediately, with nothing to check.)

Getting the hand-made bucket in the right place took three tries. The first landed in the management account. From the lab account, that showed up as an access-denied error that read like "this bucket doesn't exist". The second landed in the wrong region. Terraform's account check can't protect the console, and that was the clearest argument for this step.

One console bucket turned out to be three Terraform resources: the bucket, its public-access settings and its encryption. Importing only the bucket would have left its security settings unmanaged. Terraform generated the code, and I reviewed it like anyone else's: I removed computed fields, replaced a repeated name with a reference, and kept one setting the console chose that I wouldn't have.

Then I tested drift. By hand, I changed a tag and turned off one of the bucket's Block Public Access settings, the kind of change a hurried admin or an attacker makes. A refresh-only plan showed both changes in AWS. A normal plan showed exactly the two fixes and nothing else. I applied it and read the settings back from AWS. The limit is that Terraform only notices drift when someone runs a plan. Catching it continuously needs its own control, which I've noted as a next step.

Step 3: a locked state bucket

State moved from a local file to S3. A local file dies with the disk, can't be shared, and does nothing to stop two runs writing it at once. The state bucket is infrastructure too, so it's a chicken-and-egg problem: Terraform needs the bucket before it can store state there. I built the bucket with Terraform using local state, then moved its own state into the bucket it had just made. No hand-made pieces, and no local copy left afterward.

A bucket that holds its own record needs guarding. Terraform refuses any plan that would delete it. Every old version of the state is kept for 90 days. ACLs are off, and a policy refuses any request that isn't over HTTPS. Before deleting the local copies, I checked that the remote state's resources matched them exactly and that a plan against S3 showed no changes.

Locking uses S3 itself, with no extra database. Terraform writes a small lock object with a conditional write ("only if it doesn't exist"), so exactly one run wins. Locks never expire, so I tested the case you meet in real life: a run that crashed and left its lock behind.

The rule I took from it: before force-unlocking, read who holds the lock and when they took it. Unlocking a run that's still going is how state gets corrupted. I had planned to demo the lock with a different Terraform command, and tested it first. It doesn't hold the lock, so the demo used a hand-written one instead.

Step 4: every scanner finding gets a decision

Checkov reads the Terraform files and checks each resource against a library of rules. It never talks to AWS, so it catches problems before anything is applied. It's also code from someone else, so it ran boxed in: a container image pinned by its hash (a tag can be moved, a hash can't), no network, the code mounted read-only, not as root.

I checked the scanner's output as well. Scanning both folders in one run counted the state bucket's findings two or three times. One folder per run gave clean numbers.

"Skipped" doesn't mean "ignored". Each skip sits in the code, with a date and a reason the next reviewer can argue with. The fixes were the cheap, right changes. The accepted ones are production rules that don't fit yet. A KMS key policy adds no second gate while there's only one admin identity. Replication inside the same account doesn't stop an admin who has been compromised. Event notifications wired to nothing are just noise. The most important accepted finding is a real gap: access to the state bucket isn't logged yet. It names its fix, logging the bucket's reads and writes into the SIEM, and that's tracked as its own task. An "accepted" finding with no way back becomes a forgotten one.

In production, I would change

  • Encrypt state with a KMS key whose policy lets only the deployment roles decrypt it, and log every decrypt.
  • Log every read and write of the state bucket to the SIEM, with a detection for unexpected writers.
  • Replicate state to a separate account with Object Lock, so a compromised admin can't delete every copy.
  • Run plans in CI with short-lived credentials from the CI provider's own identity (OIDC), with no stored secrets, and detect drift on a schedule.

What I learned

  • "Apply complete" is Terraform's claim. A separate read from AWS is the evidence.
  • Clicks have no review step. Two console slips in one exercise did more to justify the code than any argument.
  • Test the tool, not your memory of it. Both my lock demo plan and my first scan results were wrong until I checked.
  • A scanner finding is a question, not a verdict. I answer each one: fix it, or write down why not and when I'll come back to it.
